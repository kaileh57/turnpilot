### Gaps

- Nobody has tested whether the CURRENT big model (Flip Flop, oid f0667cf6, 2026-10-24) takes a turn from a desire pulse alone, or at what lead distance. Every positive data point is from Cinque v2. This must be the day-1 experiment, before any steering code.
- There is no RX 9060 (chestnut) per-run time for the 775 MB big pkl. Read modelV2.modelExecutionTime on the real device before budgeting a detector inside modeld.
- No evidence that the big model stops for pedestrians under Autospeed. There is also no confirmed BeamNG way to place a moving pedestrian; only static or teleported props are plausible.
- Nav lane changes below 20 mph: LANE_CHANGE_SPEED_MIN blocks every city-speed lane change. No report proposes a tested lower threshold.
- Which road-camera sensor the comma four runs: os04c10 (1344x760, f=1141.5) or AR/OX (1928x1208, f=2648). camera.py:49-71 maps both to 'mici', so the live one is decided at runtime.
- Neither prior attempt has a real Model 3 drive log showing an engaged turn or lane change.
- Target car details are unknown: HW3/HW4, firmware version (needs 3-bit DAS_steeringControl), and whether Autosteer can be turned off.
- The test region is unknown: Report 4 assumes Seattle/Washington, while Report 2 and the fork's NAV.md use Indiana OSM tiles. This affects tile builds and lane-data coverage.
- Whether chestnut can attach to the Windows sim PC (tinygrad USB+AMD on Windows or WSL usbipd) for a PC-only big-model loop is unverified.
- Stock AEB with openpilot long: safety forwards stock DAS_control during DAS_aebEvent (tesla.h:304). This is from code only and has never been drive-tested.

### Conflicts between reports

- Routing engine. Report 2 wants to keep the hackathon's pure-Python A* router. Report 4 wants Valhalla (format=osrm) behind upstream navd's existing Mapbox-shaped parser. Report 1 wants Mapbox through MAPBOX_TOKEN. The discriminator: upstream navd already parses Mapbox-shaped steps (navd.py:53-55) and Valhalla emits that shape (osrm_ser.cc). So MAPBOX_TOKEN on day 1 and Valhalla later needs no parser change. The A* router only helps for BeamNG maps that are not OSM.
- Sim integration. Reports 2 and 5 say vendor the sim-device bridge (Lua mod, relay and harness). Report 1 says implement upstream tools/sim World/SimulatorBridge. They can be combined, but the plan has to pick one.
- Fork YOLOX weights licence. Report 2 says Apache-2.0; Report 3 says they are AV2 CC BY-NC-SA fine-tunes. Report 3 is correct (detector/device.py:36-37).
- ZMQ bridge risk. Report 1 says removing the bridge breaks the prior PC-to-device tooling, but that tooling uses its own TCP/UDP protocol (forward.py), so it does not.
- Nav alpha date: Report 1 says Oct 11, Report 4 says Oct 12. The commit is dated Oct 11 17:49 -0700.
- Turn speed limit: Report 5 says about 13 mph for a 10 m radius, using opendbc's 3.6 m/s^2. Reports 1 and 3, using controlsd's 3.0 clip, say about 12 mph. The 3.0 clip binds first.
- Turn-desire evidence: the known-facts and Report 4 treat 'desire alone turns the car' as established. Report 2 shows it rests on one Cinque v2 A/B, and the fork later reported weak, late turn-in on newer models.
- 'Chestnut' terminology: prior docs use 'Chestnut' for the big model running on Mac Metal or CUDA, not the AMD GPU. PERFORMANCE.md's 16 ms figure is not chestnut hardware timing.

### Top risks

- Desire-only turning may not work on the current big model: the only positive A/B was on Cinque v2, and there have been at least 4 model swaps since. If it fails, both prior attempts fell back to hand-drawn steering, which failed. Measure it first.
- The rising-edge pulse means the model sees one desire event when the desire is first set, so the lead distance is the only timing lever. A desire sent too early (the old flat 150 m keep) drove cars off the road.
- DesireHelper's 20 mph minimum blocks nav lane changes at city speeds. Lowering it is an untested safety change.
- The Tesla Model 3 cannot actuate blinkers (TX whitelist and the HUD TODO), so every nav lane change and turn is unsignalled unless the driver uses the stalk.
- Tight urban turns: controlsd clips lateral accel to 3.0 m/s^2 (a 10 m radius needs 12 mph or slower). If Autospeed does not slow enough, curvature saturates and the car swings wide.
- Autospeed on Tesla needs alpha long and a non-RELEASE panda build (ALLOW_DEBUG). With a release panda, longitudinal silently does nothing.
- Car firmware must have 3-bit DAS_steeringControl, or the car is dashcam-only. The sim's fake Tesla must emit 0x054 or 0x489, which simulated_tesla.py does not.
- Chestnut headroom for any pedestrian detector is unmeasured, and the device is single-tenant, so a detector must run inside modeld, which increases the upstream diff.
- Licensing: YOLO26 is AGPL for both code and weights, and the fork's YOLOX fine-tunes plus the lightd and lined weights are NC-SA. Only stock Megvii YOLOX COCO weights are clean.
- The big model runs only as the USB+AMD pkl. Pre-car sim on the Windows CUDA path cannot exercise the current big model, so sim behaviour may not transfer.

## Upstream openpilot master

Upstream openpilot master (14652aac, Oct 25 2026) already ships a "nav alpha" (commit 4c362ca32, Oct 11 2026). It includes navd (Mapbox routing at 1 Hz that publishes navInstruction and navRoute), mapsd (renders a 256x256 route map into VISION_STREAM_MAP), a NavigationEnabled param, a NavDestination param that athenad can set, and a navigation panel in the mici (comma four) UI. Start TurnPilot from this, not from the old fork. The driving model does not use nav. Both the big and small models take only new_img, desire (8-wide one-hot), traffic_convention, action_t and their own recurrent state queues (state_img_q, state_desire_q). modeld never reads the map stream. Desire still has turnLeft/Right, laneChangeLeft/Right and keepLeft/Right, but upstream DesireHelper now only ever emits laneChangeLeft/Right, and only after a blinker plus a steering nudge above 20 mph. modeld turns desire into a rising-edge pulse. So the turn-desire behaviour depends only on the hackathon's evidence (medium confidence). The smallest hook for navd-driven desire is in modeld.py, around lines 372-392, plus DesireHelper.update: a "virtual blinker" from a new nav message. Autospeed is the planner taking the minimum of MPC (leads), cruise and the e2e model accel (longitudinal_planner.py:106-112), always on. It only takes effect with openpilot longitudinal. On Tesla that is alpha long, which needs the AlphaLongitudinalEnabled param and a panda built without RELEASE=1 (ALLOW_DEBUG). Tesla angle control is good enough for city turns at turning speeds (360 deg EPS cap, about 3 to 3.6 m/s^2 lateral). It has three hard gates: Tesla software must be the 3-bit firmware or the car is dashcam-only, Autosteer must be off, and there is no blinker actuation. tools/sim has a clean World/SimulatorBridge ABC that a BeamNG bridge can implement. Its SimulatedCar is a Honda Civic, so testing Tesla behaviour needs a SimulatedTeslaCar that emits the right addresses. The ZMQ cereal bridge was deleted on Oct 24, 2026 and replaced by a webrtc bridge.

### Risks

- The turn-desire response is untested by upstream code: DesireHelper never emits turnLeft/Right/keep*, so how the current 880M model reacts depends only on the hackathon's BeamNG evidence; it may have been trained without those desires.
- No turn-signal actuation on the Tesla port: nav-triggered lane changes and turns will happen with no blinker (a legal and safety issue). Adding blinker CAN to the Tesla CarController and panda safety TX list is a much bigger diff.
- Tesla software must be the 3-bit DAS_steeringControl firmware (HW3 2026.8.6 or later) or the car is dashcam-only. Autosteer must be off in the Tesla UI.
- Autospeed on Tesla needs alpha long plus a debug (non-RELEASE) panda build. Installing a release panda firmware silently disables longitudinal control.
- Tight city turns: the 3.0-3.6 m/s^2 lateral limits mean turns of 10 m radius or less must be taken at about 12 mph or slower. If the model enters faster, curvature is clipped and the car swings wide.
- 1 Hz GPS (qcomgpsd) and 1 Hz navd are too coarse for desire timing about 2.5 s before a maneuver; dead reckoning is needed.
- The chestnut big model already uses about the full 50 ms budget, and the AMD device belongs to modeld, so a traffic-light or pedestrian net cannot easily share it.
- No explicit pedestrian handling: radar is unavailable on most Model 3s, and vision leads are vehicles.
- The upstream nav alpha depends on comma API (DongleId) tiles and routes, or a Mapbox token. In sim, mapsd fails harmlessly, but navd needs MAPBOX_TOKEN.
- lateralManeuverPlan overrides steering whenever its service is valid. A stray publisher would hijack steering.
- The ZMQ bridge was removed 2 days ago. Any PC-to-device tooling from the previous attempt that relied on it is broken on master.
- Upstream is moving fast (nav alpha 2 weeks old, Autospeed unreleased), so rebasing will touch modeld, desire_helper and navigation often. Keep the hooks small.

- Which GPS does comma four use: ublox on /dev/ttyHS0 (10 Hz gpsLocationExternal) or qcom (1 Hz gpsLocation)? Check on the device.
- Does the current big model still respond to turnLeft/turnRight/keepLeft/keepRight desire pulses on real roads, and at what lead time?
- Does comma's nav API (API_HOST/v1/nav) need comma prime or just a registered dongle? A personal Mapbox token avoids the question.
- What Tesla software version and HW (HW3 or HW4) is on the target Model 3?
- Can the precompiled big pkl run on the Windows sim PC (retargetable artifacts? CUDA, as the old sim-device claimed), or must sim use the small model?
- Will upstream soon ship a map-input model that consumes VISION_STREAM_MAP? That would make turn guidance native and change the plan.

### Risks

- Desire-only turning may not work on the current 0.11.x big model. The single positive A/B used Cinque v2, and the fork reports weak or late turn-in. If it fails, the temptation is to rebuild hand steering, which failed in both attempts.
- The BeamNG bridge has not been verified on the target Windows + BeamNG.tech + comma four + chestnut setup. The last-known-good topology needed a Mac in the middle, and running over wifi with the adapter on the device limited it to 2-5 frames/s.
- The bridge depends on a private repo (kaileh57/openpilot-sim-harness) and pinned patches against specific harness revisions. Setup-pc.ps1 refuses to run over unrelated edits.
- Sim-only steering overrides (470 deg, 0.24/m) could leak into the car build. The real Model 3 limit is 360 deg.
- The lane-count rule was tuned to BeamNG's road-width perception (6-7 m read on a 4.4 m road). Thresholds may be wrong on a real car.
- Routing: a pure-Python A* on OSM XML for a whole region may be slow or memory-heavy on the comma. Valhalla needs pyvalhalla on the device plus tile builds, and the fork's build script is missing.
- Lights and stop signs would rely entirely on upstream model longitudinal. NC-licensed lightd/lined weights must not ship if the project's commercial status changes.
- The fork's tests were not run here, so none of its claimed behaviour is verified. The person detector has no drive evidence at all.
- Rule for the next attempt: one integrator, at most 2-3 agents, a single repo and branch flow, and no cross-machine postbox or handoff protocols.
- Rule: upstream touches limited to modeld desire, desire_helper, custom.capnp, services.py and process_config entries. Every other change lives in new files. Rebase weekly. Never fork submodules such as msgq.
- Rule: no hand-written steering blend. The only route-to-model inputs are desire and lane-change direction. If the model won't turn, fix desire timing or pulse shape, and measure before adding anything.
- Rule: evidence means a drive outcome. Show route completion, turns taken out of turns attempted, and disengagements in BeamNG with a saved rlog and video, not deploy hashes or health JSON. Each feature needs a scripted BeamNG scenario before it merges.
- Rule: no feature flag, latch or fail-closed scaffolding until a feature works end to end. Keep one param for nav on/off.
- Rule: drop lights, stop signs, mapnet, the nav head and speed zones from scope. Use upstream Autospeed. Add pedestrians only by reusing an existing detector inside modeld.
- Rule: pin one model version and one openpilot base for the whole build, and record them in the README.

## Vision and detection

YOLO26 is Ultralytics' NMS-free, DFL-free detector, released January 14, 2026 in ultralytics 8.4.0. Its code and weights are AGPL-3.0 unless you buy an Enterprise license, and Ultralytics says models trained with its code are AGPL too. A public open-source fork can comply, but the fork stops being purely MIT and nothing in it can go upstream. comma's own MIT starter (comma_hack_7) already runs yolo26n.onnx through tinygrad's OnnxRunner on the chestnut, at 7.02 ms for a 320x320 input. That starter does not run on the device: it streams camera frames from the comma over WebRTC/SSH to a PC and imports ultralytics/torch at inference time. The key architectural fact is that the chestnut can only be used by one process. tinygrad claims the USB interface exclusively, so any detector on the chestnut must be a small hook inside modeld that reuses the frame modeld has already uploaded. This is exactly what the previous fork did, and that part is worth keeping. Keep these pieces of the fork: person_stop.py (planner logic with no messaging dependencies, tested), decoder.locate() ground-plane ranging, device.py's calibrated warp views (narrow f=700, wide f≈353), compile_detector.py, the PersonAhead capnp struct and the one-line planner candidate. Its stock Megvii YOLOX-tiny ONNX is Apache-2.0 and a risk-free fallback, but its fine-tuned weights were trained on Argoverse 2 (CC BY-NC-SA) and need a licence decision. The fork's chestnut, sim and closed-loop test results were never filled in. Letterboxing the whole frame to 320 is too low-resolution for pedestrians past about 20 m, so swap the YOLO26 ONNX in behind the fork's calibrated view warp. Deformable-attention DETRs (RT-DETR, D-FINE, RF-DETR) are Apache-2.0 at the smaller sizes, but tinygrad's ONNX frontend has no GridSample, so they are not drop-in. Nobody has measured the big model's runtime on the chestnut, so whether a 10 Hz detector fits in the 50 ms cycle is the main unknown. Measure it first. Upstream still lists pedestrians as a limitation, and whether the 880M model stops for them under Autospeed is unverified. Test that in BeamNG before building anything.

### Risks

- Licence: YOLO26 weights and code are AGPL-3.0, which makes the fork AGPL-encumbered, blocks upstreaming to MIT openpilot, and needs an Enterprise license for any commercial use. The fork's AV2 fine-tuned YOLOX weights are CC BY-NC-SA-derived (non-commercial).
- Unmeasured compute: the big model's run time on the chestnut is unknown. If it is above about 35-40 ms, there is no room for a detector in the 50 ms modeld cycle, and the fork's skip rule (driving model over 30 ms) would quietly starve the detector.
- Single-tenant chestnut: a separate detector process cannot share the GPU, so the detector has to live inside modeld, which adds to the diff against upstream modeld.
- If the detector runs in modeld and fails or falls back to the small model, personAhead goes stale. The fork handles this with an 'unavailable' alert. Keep that so a missing detector never reads as 'no pedestrian'.
- Monocular range error is large: the fork's gate measured vehicle range p95 error of 47%. Pedestrians beyond about 25 m on a full-frame 320 input are unreliable. Use the warped narrow view.
- Input format: YOLO26 expects RGB 0-1 while the fork's warp outputs BGR 0-255 for YOLOX. Getting this wrong silently ruins detection quality.
- Testing gap: the fork never ran sim, chestnut or closed-loop tests for the detector. BeamNG's pedestrian support is unverified, so testing before the car may be limited to static props.
- Version skew: comma_hack_7 pins tinygrad cc32aa18 and pickles its own JIT, while openpilot vendors a different tinygrad. Compile with openpilot's tinygrad_repo or the pickles will not load.

- What is modelExecutionTime for the 0.11.2/0.11.3 big model on the chestnut with a comma four? Read modelV2.modelExecutionTime from a real chestnut route, or run compile_detector.py's benchmark on the hardware.
- With the big model under 0.11.3 Autospeed, does the car slow or stop for a pedestrian in its path? Test in BeamNG, if it can place pedestrians, by watching modelV2.action.shouldStop and desiredAcceleration before committing to a detector.
- Is AGPL acceptable to the user for a public kaileh57 repo, or should we default to Apache-2.0 YOLOX-tiny or RF-DETR-Nano? RF-DETR would need GridSample in tinygrad.

- Does YOLO26's ONNX export at a rectangular imgsz with nms=False work through openpilot's vendored tinygrad OnnxRunner? The starter only proves square 320 on tinygrad cc32aa18.

## Navigation and routing

The most important finding is that comma put navigation back into upstream openpilot master on Oct 12 2026, in PR #39066 "nav alpha". It lives in openpilot/selfdrive/navigation/ (navd.py, route.py, mapsd.py and PMTiles renderer files) and is enabled by the developer toggle NavigationEnabled. The NavDestination param is set by the athena RPC setNavDestination. navd publishes navInstruction and navRoute at 1 Hz from Mapbox Directions v5 JSON, going through comma's proxy or a MAPBOX_TOKEN env var. mapsd renders a 256x256 route map into VisionIPC VISION_STREAM_MAP, but nothing consumes it: the current 880M driving model has no map or nav input. That means the desire pulse is the only hook, which confirms the hackathon lesson. turnpilot-internal branched at ec95db3f (Oct 2), before nav alpha, and rebuilt all of this itself (about 9k lines in turnpilot/nav and turns). It should be dropped in favour of upstream's module. The best routing piece is Valhalla (MIT). With format=osrm, shape_format=geojson and banner_instructions=true it returns the same Mapbox-shaped steps, bannerInstructions and sub.components[type=lane] that upstream navd already parses. Swapping Mapbox for Valhalla is therefore a rewrite of calculate_route's request (POST /route with a JSON body, or in-process pyvalhalla Actor.route), not a parser rewrite. pyvalhalla 3.9.1 has cp312 manylinux_2_28 aarch64 wheels, which matches openpilot's Python 3.12 pin. The forks are worth little for routing. sunnypilot ships upstream nav alpha plus pfeiferj mapd and has an empty nav settings page. FrogPilot keeps the old 0.9.x Mapbox navd with the old SNPE nav model. dragonpilot has no nav. All three are MIT. pfeiferj/mapd v2.3.1 (MIT, Go, offline OSM) is the right drop-in for curve and speed-limit speeds, and it does no routing. Recommended minimal pipeline: (1) rebase onto current upstream and turn on NavigationEnabled. (2) Day 1 uses MAPBOX_TOKEN, which needs zero code. Day 2 points calculate_route at Valhalla: a PC or LAN server on the bench, then pyvalhalla on-device with a Washington-state tile tar for the car. (3) Add one small 'navdesire' bridge, around 100 lines. It tracks progress with upstream's RouteTracker, dead-reckons the distance to the next maneuver with vEgo between 1 Hz updates, and maps type/modifier to turnLeft/turnRight/keepLeft/keepRight using the hackathon timings: keep lead max(2.5 s*v, 20 m), turn desire within about 25 m of entry. It feeds DesireHelper/modeld's desire_pulse, with nav-triggered lane changes going through the existing blinker-style laneChange path. (4) Destinations come from athena setNavDestination via a small laptop or phone script, or a tiny LAN HTTP page; connect's UI doesn't send destinations yet. (5) Optionally add mapd for curve speeds. Delete the hand-drawn turn path and curvature blend.

### Risks

- navd runs at 1 Hz and navInstruction is published at 1 Hz, which is up to 30 m of slop at 30 m/s against a 2.5 s lead. The desire bridge must dead-reckon maneuverDistance with vEgo at 20 Hz, or navd's Ratekeeper and the services.py rate must be raised.
- GPS latency and error: the turn desire window is only about 25 m, and urban-canyon GPS error in Seattle can reach 10-20 m. Use the RouteTracker projection (it never goes backwards) and gate the turn desire on the model also seeing the junction, as the hackathon's camera-driven gating did.
- The desire is a rising-edge pulse in modeld (modeld.py:197-200). Holding the desire high does not re-trigger it, so it has to be sent at the right moment, and once sent the model owns completion. A desire sent too early (the hackathon's earlier flat 150 m keep lead) drove cars off the road.
- comma's Mapbox proxy (API_HOST/v1/nav) and the PMTiles tiles endpoint may need comma prime or may be rate-limited for an alpha. Assume MAPBOX_TOKEN or Valhalla from day 1. mapsd is not needed for driving.
- Upstream nav alpha is two weeks old and may change shape or be reverted. Keep the TurnPilot diff to the calculate_route patch plus a separate desire-bridge file so rebases stay clean. One web summary claimed an Oct 14 revert, but it is not in master as of Oct 25.
- On-device pyvalhalla on the comma four is untested beyond the fork's doc. Risks are memory and CPU next to the big-model pipeline, and wheel import on the read-only system Python. The fallback is Valhalla on a phone or laptop, or the FOSSGIS public server (1 request/s, not for production).
- OSM turn:lanes covers only about 26% of Seattle arterial ways, so lane choice must fall back to the turn side when lanes are missing. Wrong lane info leads to an unnecessary lane change.
- Do not modify the msgq layout or the cereal reader count. The old fork did, and it broke the prebuilt mapd binary (turnpilot-internal process_config.py:261).
- BeamNG maps are not OSM, so sim routing needs either a BeamNG-to-OSM export plus Valhalla tile build, or a stub router. Otherwise the sim exercises a different routing path than the car.
- NavDestination clears on manager start and on the offroad transition, so the destination has to be re-sent after every reboot or ignition cycle.

### Open questions

- Does the comma four run ubloxd (gpsLocationExternal at 10 Hz) or qcomgpsd (gpsLocation at 1 Hz)? This decides how much dead-reckoning the desire bridge needs.
- Does Valhalla's osrm output include the lane sub-banner without turn_lanes=true? Verify with one request against WA tiles.
- Does comma's /v1/nav Mapbox proxy work for non-prime devices during nav alpha?
- Will comma connect add a destination-send UI soon (the toggle text promises one)? If not, use an athena JSON-RPC script or a LAN page.
- Should nav-driven lane changes reuse DesireHelper's laneChangeStarting path (blinker-equivalent, blindspot check) or send laneChangeLeft/Right pulses directly? Tesla's angle steering and BSM availability affect this.
- Will pyvalhalla plus a roughly 300-500 MB WA tile tar fit alongside the big-model workload on the comma four (RAM and /data space), or should routing run on the phone or PC?

## Testing, BeamNG and the car

Reuse the September sim-device bridge, which puts the real comma four in the loop. It is close to current upstream: the device ran upstream a39561058 from Sep 18 2026, only 128 commits behind master. Do not build a new BeamNG.tech/BeamNGpy integration. The old setup used BeamNG.drive 0.39 with a custom Lua mod (RenderView saved as JPEG, plus a UDP/TCP relay), not BeamNG.tech. On the comma, one Python process replaced camerad, sensord and pandad and sent CAN for a simulated Tesla Model 3. Two upstream changes break it. First, opendbc dropped 2-bit Tesla steering firmware on Sep 20 2026, so the simulated car must also send DI_autonomyHealth (0x054), or openpilot fingerprints it as dashcam-only. Second, BeamNG.drive 0.40 shipped Oct 19 and disables mods on update. Upstream now ships the big model only as a precompiled USB+AMD tinygrad pkl with no ONNX, so the big model cannot run on the PC's CUDA GPU as the old WSL2 path did. Recommended ladder: (1) open-loop replay plus unit tests, (2) BeamNG with the comma in the loop at stock limits, (3) shadow-mode drives in the car (navd on, driver steering), (4) parking lot, (5) empty streets, (6) supervised routes.

### Risks

- Sim and car mismatch: the old sim ran raised steering limits (5 m/s^2, 10 deg per frame, 470 deg lock, 0 actuator delay). With stock limits the car may not make tight city corners at Autospeed's chosen speed. Validate at stock limits, or turns that pass in sim can fail in the car.
- The current big model runs only with DEV=USB+AMD (precompiled pkl). A Windows/WSL2 PC sim cannot run it, so big-model desire behavior can only be verified with chestnut on the comma or on a Linux PC. The small model may respond differently to turn desire.
- The big pkl is a 775 MB LFS artifact that is 'only built for releases'. A fork must carry it, or the chestnut stays UNCOMPILED and modeld falls back to the small model.
- Real Model 3 firmware must have 3-bit DAS_steeringControl (HW3/HW2.5 2026.8.6 or newer), or openpilot is dashcam-only. Tesla OTA changes can break support without warning.
- Alpha longitudinal is required for Autospeed and is hidden on release branches, so the fork must run as a dev branch. It also replaces the stock DAS_control. Whether stock AEB stays functional with openpilot long on Tesla is unverified; check before street tests.
- A firm steering override fully disengages on Tesla, so a driver correcting a bad turn ends the engagement. Plan the test protocol around that.
- Wi-Fi link to the comma: chestnut takes the comma's USB-C port and powers it, so wired networking is likely unavailable. Frame age (119 ms median in the old setup against modeld's assumed 50 ms) makes sim timing optimistic or pessimistic relative to the car.
- BeamNG.drive 0.40 (Oct 19 2026) disables mods on update and may change Lua or RenderView APIs. The old mod was built for 0.39. Pin the game version, or check on day 1.
- BeamNG.tech licensing: free only for academic, non-commercial use. A company project may need a commercial license, so default to BeamNG.drive.
- Pedestrians: neither BeamNG.drive nor BeamNG.tech has pedestrian AI. Prop-based tests prove little about real pedestrian behavior, and real-car pedestrian testing must be extremely conservative (prop or cardboard target in an empty lot only).
- The driving model has no explicit pedestrian output; pedestrian handling is implicit in the e2e longitudinal output. Adding a YOLO-based pedestrian stop is new safety-critical code, and the YOLO26 weights carry AGPL licensing.
